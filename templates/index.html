About this tool

Transportation Performance is an interactive dashboard for monitoring P&G North America intersite shipment execution. It pulls the OCNA shipment tracking table from Databricks (hive_metastore.userdb_essam_ae.ocna_shipment_tracking_intersite) into memory and serves analytics over a single TMS-load-level dataset.

Every row in the source represents one TMS load. The same order can appear on multiple loads. All measures below are computed at load grain.

Tabs

1. Performance Review

  • KPI strip — overall SOT 1st, SOT Final, IOT, and # Shipments for the filtered population.
  • Carriers panel — per-carrier KPIs with split attribution (see Measures below).
  • Lanes panel — per-lane KPIs. Lane = shipping_plant → destination_plant.
  • Trend Explorer — day-by-day SOT 1st / SOT Final / IOT for the selected carrier, lane, or service type, with reason-code breakdown.
  • Carrier Reassignments — at the bottom, ranks carriers (and lanes) by how often a load was reassigned off them after the first commitment.

2. Order Analysis

Per-load timeline: Old Pickup (1st commitment) → New Pickup (final commitment) → Actual GI (gold-layer load complete date) → SAP Actual GI → Requested Delivery → Actual Arrival. Loads whose dates contradict each other are flagged with a ⚠ badge.

3. Operational Review

Data Quality & Date Anomalies. Surfaces loads whose milestone dates are internally inconsistent (e.g. arrived before goods issue, shipped before its pickup commitment). The ship event is the Actual GI = gold-layer load complete date, which matches the SAP actual goods-issue date (cdl_oss_prod.silver_sap_n6p.likp.wadat_ist) on 97.8% of loads. Each flagged load is also cross-checked against that SAP GI; the "SAP resolves?" flag shows whether the SAP GI date corrects the contradiction.

Measures — how they are calculated

The ship event used by SOT is the Actual GI = gold-layer load complete date (matches SAP actual GI on 97.8% of loads), falling back to the trailer check-out date only when load complete is missing.

MeasureDefinitionAttributed to
SOT 1st
Ship-On-Time vs 1st commit		 % of loads shipped on or before the first committed pickup date.
hit = (actual_gi ≤ old_pickup_date)
eligible = actual_gi AND old_pickup_date both present
SOT 1st = sum(hit) / sum(eligible) × 100
 old_carrier_name — the carrier who made the first commitment.
SOT Final
Ship-On-Time vs final commit		 % of loads shipped on or before the final committed pickup date.
hit = (actual_gi ≤ newest_pickup_date)
eligible = actual_gi AND newest_pickup_date both present
SOT Final = sum(hit) / sum(eligible) × 100
 newest_carrier_name — the carrier on the final commitment.
IOT
Inventory On Time		 % of measurable loads where iot_on_time = "Yes".
hit = (iot_on_time = "Yes")
eligible = iot_on_time ∈ ("Yes", "No")
IOT = sum(hit) / sum(eligible) × 100
 newest_carrier_name — the carrier who physically delivered.
# Shipments Count of loads in the current filter scope. Lane / dataset = load count. Carrier = loads where the carrier was the final carrier (delivered). When the first-commit and final-commit populations differ, the cell is marked with a * and the tooltip shows both counts.
# Dropped
(Reassignments panel)		 Count of loads where the old carrier was changed before the load shipped.
drop = (old_carrier_name set AND newest_carrier_name set AND old ≠ new)
 Always to the old_carrier_name (the carrier who lost the load) and to the lane_pd the load was on.

Why "split attribution" matters

Whenever Logistics reassigns a load between the first and final commitment, the carrier on the first commitment and the carrier on the final commitment differ. SOT 1st belongs to the first carrier (they made the promise); SOT Final and IOT belong to the final carrier (they kept the promise and delivered). If we attribute all three measures to a single carrier per load, we end up scoring carriers on commitments and outcomes they never owned.

Concretely, for any load L and any carrier C:

SOT 1stC  numerator/denominator runs only over loads where old_carrier_name = C
SOT FinalC  numerator/denominator runs only over loads where newest_carrier_name = C
IOTC     numerator/denominator runs only over loads where newest_carrier_name = C

Network-level KPIs (the top strip) are unchanged by this. Only the per-carrier breakdown shifts. A no-reassignment subset (loads where old_carrier_name = newest_carrier_name) produces identical numbers under both methodologies — this is the integrity check.

Filters

  • Shipping Plant, Destination Plant, Lane (Plant → Plant), TMS Carrier, Service Type, Destination City, Is Oral Care?, Load Number.
  • All filters are multi-select and search-as-you-type; combining filters AND-narrows the rows.
  • Filters apply across all sections including the Trend Explorer and Reassignments panel.

Trend window

  • The "anchor" date is the most recent Actual GI (load complete date) present in the loaded data.
  • Past Week = 7 days ending on the anchor. Past Month = 30 days ending on the anchor.
  • Daily series are bucketed by Actual GI (load complete date).

Reason codes

The reason table on the Trend Explorer counts rows by csot_failure_reason_updated for the selected carrier / lane / service in the chosen window. Empty values show as (blank).

Data freshness

The dataset is fetched once from the Databricks SQL warehouse and pickled locally. The footer of the header shows "Data as of <timestamp>". To refresh, re-run python data_loader.py --refresh and restart the app.

Tech stack

  • Python + Flask backend (in-memory analytics over ~30k loads).
  • Single-page HTML / Vanilla JS / Chart.js frontend, P&G-branded.
  • Databricks SQL warehouse for source data; local pickle cache for fast restarts.
